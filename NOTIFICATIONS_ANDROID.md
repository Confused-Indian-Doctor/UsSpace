# Android push delivery in v0.14

The existing paired Firebase app now has real Firebase Cloud Messaging data-only delivery. `UsMessagingService` receives server-sent messages; a short unique WorkManager job checks current Firebase authentication, a server-read user/couple association and server-read membership before posting an Android notification. No Firestore listener manufactures a local notification instead of a push.

Notifications are opt-in. The private per-user preferences document and native cache supply the master switch, seven independent categories (pings, notes, status, goals, bucket, memories, calendar), and quiet hours in the selected IANA time zone. Android 13+ additionally asks for `POST_NOTIFICATIONS` permission only after an explicit settings action. Android’s app and channel controls also apply. Enabled quiet hours with invalid values fail closed. An overnight interval includes its start and excludes its end; identical start/end times mean an entirely quiet day. DST is calculated using the selected zone.

Each category has a separate Android channel. Lock-screen text is generic, including on devices that display private notification content. Remote title/body values are never used as notification text. Health, Cycle, mood selections, draft letters, contacts, raw rota details, note bodies, goal text and photo data are never copied into notification copy or routes.

The native installation identifier is a random private UUID. Tokens are bound to `users/{uid}/devices/{installationId}` only after opt-in, permission and current membership verification. Token rotation schedules a background registration job with the same guards; it does not require reopening the app. Account changes and pairing revocation disable the old binding and remove the local Firebase token. `beforeSignOut` disables the device before the Firebase account is cleared, marks that account blocked for local delivery, deletes the token, cancels existing notifications and continues sign-out once, with a five-second maximum wait if the network is unavailable. The server delivery function independently checks current membership and private preferences. Firebase tokens never cross the JavaScript interface or enter logs.

Cloud Function retry identifiers are SHA-256 event IDs. Unique WorkManager jobs, persistent per-account delivered IDs retained for the entire 24-hour message validity window, stable Android notification identity and `setOnlyAlertOnce` prevent repeated alerts on retries. Pending-intent identity includes the complete event hash. Old or invalid envelopes, another account’s notifications, stale pairing and arbitrary route/URL attempts are rejected. When a notification is tapped, its route waits for the bundled page to finish loading and is checked against the current account and server pairing before navigation.

`UsNotifications.sendPing()` is an explicit shared action. It writes only a UUID, the Firebase-derived sender UID and a server timestamp to the existing couple’s `usPings` collection. The other partner’s opt-in, category settings and quiet hours determine whether the deployed server function sends a push. The existing realtime love counter remains available even when push notifications are off.

## Integration

MainActivity instantiates `NotificationBridge(Activity, WebView)`, registers it as `UsNotifications`, and delegates bundled-page completion to `onPageReady`, launch/new intents to `handleIntent`, notification permission results to `onRequestPermissionsResult`, and destruction to `close`. Authentication calls `beforeSignOut(Runnable)` before its existing sign-out logic. The web UI listens for `window.onUsNotificationState` and `window.onUsNotificationOpen` and refreshes native delivery after preference changes. The preferences bridge also emits a package-scoped preferences-changed broadcast, with only the UID.

The manifest includes `POST_NOTIFICATIONS` and a non-exported `UsMessagingService` with the Firebase messaging action. The app adds `firebase-messaging` and `androidx.work:work-runtime:2.10.1`. Firebase Messaging automatic initialization should be disabled in manifest metadata by default; an explicit opted-in registration still uses `getToken`, and `deleteToken` clears it on sign-out.

Actual partner push delivery requires the updated Firestore rules and a trusted server dispatcher. The `functions/` backend supports either deployed Firebase Cloud Functions (which require the Blaze plan) or the optional `functions/worker.js` process hosted on a trusted external server using server-only Firebase Admin credentials. The external worker is compatible with the existing Spark project and sends the same real FCM data-only envelopes; credentials stay on its host and are never placed in the APK or repository. It quietly baselines existing documents at startup, uses a singleton dispatch lease and persistent change cursors, and applies the same account, pairing, token, category and quiet-hours checks. See [PUSH_SETUP.md](PUSH_SETUP.md) for the required server configuration.

A build/emulator test can verify Android permission, settings, channels, route boundaries and policy, but it cannot claim successful real-phone delivery without an active trusted dispatcher and two opted-in paired Google accounts.

The production Java boundary is exercised by `firebase-tests/NotificationPolicyTest.java`, including current-recipient identity, private-field rejection, route mismatch, message expiry, quiet intervals, India time, UK DST, master/category/permission gates and retry identity.
